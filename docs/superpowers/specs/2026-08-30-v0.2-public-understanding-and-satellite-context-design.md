# Territorial Score V0.2 — Public Understanding + Deterministic Satellite Context

Date: 2026-08-30
Status: design approved in chat; implementation not started
Target branch: `feat/v0.2-satellite-context`

## 1. Purpose

V0.2 turns Territorial Score from a technically correct but expert-oriented demo into a public-facing, self-explanatory territorial context experience.

The primary audience is a non-specialist visitor, recruiter, product reviewer, or decision-maker opening the public URL without prior explanation.

The release must answer, in this order:

1. What is Territorial Score?
2. Where am I?
3. What do we know at this point?
4. What is missing or unverified?
5. How do signals change along the corridor?
6. What part is an ML experiment rather than territorial evidence?
7. Where did each value come from and what are its limitations?

The product identity remains: **score means musical score / partitura, not risk score**.

## 2. Product principle

Territorial Score represents independent signals aligned in space and time.

Each track is evidence or context, not an automatic conclusion.

Canonical integrity rules remain mandatory:

```text
signal != conclusion
correlation != causality
missing != zero
modelled != observed
simulation != operation
anomaly candidate != road defect
human signal != official instruction
satellite signal != road condition
snow-like != snow on road
snow-like != road closed
satellite context != safety assessment
cloudy/missing != clear
derived != observed in field
PENDING != open
PENDING != closed
PENDING != safe
```

No V0.2 UI, contract, artifact, or copy may encode or imply route safety, transitability, authorization, road condition, road closure, road defect, or aggregate risk.

## 3. Public entry experience

### 3.1 Full-screen intro card

On first entry in a browser session, the application presents a full-screen welcome card before the dashboard.

Required content:

- title: `Territorial Score`;
- short phrase explaining it as a territorial "score" / partitura;
- plain-language explanation that the system aligns terrain, weather, access, movement, evidence, and satellite context in space and time;
- explicit statement that it does not calculate a risk score;
- one sentence explaining that the purpose is to show what is known, what is missing, and where each value came from;
- short capability cards that communicate the technical stack by capability rather than a technology-name dump:
  - interactive corridor map;
  - separate data layers/tracks;
  - satellite processing;
  - auditable ML experiments;
  - versioned/validated artifacts;
  - visible sources and limitations.

Required interaction:

- primary CTA: `Explore the corridor`;
- secondary close affordance may exist;
- short visual transition into the main application;
- once dismissed, the intro remains dismissed for the current browser session;
- a persistent `What is this?` control in the application can reopen it.

The intro must include the concept:

> Each row is an independent signal. Together they describe context; they do not automatically produce a decision.

## 4. Main-screen information hierarchy

The application must follow this narrative order:

```text
WELCOME
  -> CORRIDOR
  -> SELECTED PLACE
  -> WHAT WE KNOW / WHAT IS MISSING
  -> TERRITORIAL SCORE
  -> ML EXPERIMENT
  -> PROVENANCE
```

The UI must prioritize human meaning before internal identifiers or schema terminology.

## 6. Selected-place panel

The current expert-oriented `CONTEXT FRAME` panel becomes a public-facing selected-place explanation.

Example structure:

```text
NODO ALTO
RN150 · Agua Negra
km 66.6 · 4,048 m
San Juan, Argentina

WHAT WE KNOW
...
```

Each domain card contains:

1. domain name;
2. human-readable value/state;
3. one-line explanation;
4. source/provider summary;
5. evidence state as secondary metadata;
6. an optional technical-details disclosure.

### 6.1 Relief

Example:

```text
RELIEF
4,048 m
Estimated elevation
Source: Copernicus DEM / Open-Meteo elevation workflow
DERIVED
```

### 6.2 Weather

V0.2 must explain absence instead of showing the ambiguous combination `MISSING / MODELLED` without context.

Public text should communicate:

- no frozen weather observation/model snapshot is stored for this version at that selected context;
- GeoPlatform may expose runtime model output, but runtime data is not silently reused as frozen evidence;
- modelled weather does not establish observed road conditions.

### 6.3 Mobility

Public text must state:

- no real operational vehicle telemetry is represented in the territorial track in this dataset;
- the rule/ML candidate experiment is synthetic and is a separate experiment section;
- synthetic mobility results are not live movement evidence.

### 6.4 Access

`PENDING` is rendered as a clear human statement such as `Real access status not verified`.

The UI must explicitly state that the dataset contains no frozen authoritative source sufficient to assert open/closed/safe/authorized status.

### 6.5 Evidence

Public evidence labels should be understandable (`Official reference`, `Derived along route`, etc.). Raw source references and commit hashes move to technical provenance.

## 7. Territorial Score matrix

The matrix remains the core product metaphor and becomes more legible.

### 7.1 Columns

Columns show:

- public location name;
- distance in km;
- selected-state affordance.

### 7.2 Rows

Primary rows in V0.2:

1. `RELIEF`
2. `WEATHER`
3. `SATELLITE`
4. `MOBILITY`
5. `ACCESS`
6. `EVIDENCE`

The matrix displays a human-readable primary value and a smaller technical evidence state.

Examples:

```text

```

```text

```

```text

```

Each row has a lightweight `?` help affordance explaining what that signal means and what it does not mean.

## 8. ML experiment separation

`RULE CANDIDATE` and `ML CANDIDATE` are removed from the primary territorial score matrix.

They become a distinct section titled along the lines of `Detection experiment`.

Public summary explains:

- the benchmark uses synthetic mobility data;
- a simple deterministic rule is compared with Isolation Forest;
- candidate outputs are not territorial facts and are not road-defect detections.

Collapsed/secondary technical view may include:

- detector name/version;
- candidate time window;
- supporting features;
- anomaly score;
- precision/recall/F1 from the frozen benchmark;
- limitations;
- model artifact reference;
- synthetic experiment evidence state.

Ground truth remains offline evaluation material and is never rendered as observed operational truth.

## 9. Satellite architecture

### 9.1 Architectural choice

V0.2 uses a dedicated, versioned `SatelliteContextArtifact` rather than forcing all satellite metadata into the generic single-value `TrackSample` contract.

GeoPlatform / Google Earth Engine is used as an acquisition and processing source only.

Territorial Score must not call GeoPlatform or GEE at runtime to populate satellite evidence.

Canonical flow:

```text
GeoPlatform / GEE
      -> offline/read-only snapshot generation
      -> frozen SatelliteContextArtifact
      -> strict runtime validation
      -> TerritorialDataset
      -> alignment/context
      -> UI
```

No private GEE credentials or GeoPlatform credentials may be exposed in the browser.

### 9.2 Manifest

V0.2 introduces a `SATELLITE_CONTEXT` dataset artifact kind and a manifest entry similar to:

```json
{
  "satelliteContext": {
    "path": "satellite-context.json",
    "kind": "SATELLITE_CONTEXT",
    "required": true
  }
}
```

The artifact is required at the dataset level for the V0.2 public release. Individual segment observations may still be explicitly unusable/missing.

### 9.3 Artifact structure

The satellite artifact must include, at minimum:

```text
schemaVersion
artifactId
source
  provider
  processingSystem
  sourceRef
scene
  sceneId
  acquiredAt
  cloud metadata
processing
  processorVersion
  ruleVersion
  index definitions/version
segments[]
limitations[]
```

Each segment record includes:

```text
segmentId
usable
surfaceClass | null
indices | null
  ndvi
  ndwi
  ndsi
evidenceState
reason | null
limitations[]
previewRef | null
```

Strict unknown-field rejection remains the default.

### 9.4 Surface classes

V0.2 uses deterministic, cautious classes:

- `SNOW_LIKE`
- `WATER_LIKE`
- `VEGETATION`
- `BARE_GROUND_LIKE`
- `UNCLASSIFIED`
- `MISSING`

Classification uses explicit, versioned rules over frozen spectral values.

No classifier ML is used in V0.2.

Thresholds must be documented and testable. Ground truth is not assumed from the rule output.

### 9.5 Indices

Initial public satellite context may include:

- RGB preview;
- NDVI;
- NDWI;
- NDSI.

GeoPlatform already exposes Sentinel-2 RGB, NDVI, NDWI, additional indices, scenes, stats, and time-series infrastructure. The V0.2 snapshot flow should reuse that acquisition capability where practical, while keeping Territorial Score runtime independent.

### 9.6 Missing/unusable scenes

A segment must fail closed when the scene is unsuitable.

Examples of explicit unusable reasons:

- excessive cloud cover;
- missing coverage;
- invalid/missing index values;
- processing failure;
- no qualifying frozen scene.

Unusable satellite context is rendered as `MISSING`; it must never be inferred as clear conditions.

## 10. Satellite preview

The selected-place satellite card includes a `See satellite image` interaction when a frozen preview exists.

The preview must be a versioned artifact associated with the frozen scene/processing metadata.

The UI must not load a mutable live tile endpoint as evidence for the V0.2 dataset.

## 11. Contract and core changes

V0.2 is an explicit contract version evolution, not a UI-only patch.

Expected affected boundaries include:

- dataset artifact kinds;
- manifest schema;
- satellite artifact schema;
- `TerritorialDataset` loader output;
- alignment model;
- context selection;
- human-readable location metadata;
- score rendering;
- provenance rendering.

The existing V0.1 dataset/contract compatibility strategy must be explicit in implementation planning: either support both manifest versions or introduce a new versioned Agua Negra V0.2 dataset directory. The preferred design is to keep the existing V0/V0.1 artifact snapshot immutable and add a new versioned dataset snapshot for V0.2.

## 12. Provenance UX

Raw GitHub paths, SHAs, and technical source references are not primary public copy.

Public display examples:

- `Copernicus DEM · elevation context`
- `Sentinel-2 · processed through Google Earth Engine`
- `GeoPlatform corridor inventory`

A `Technical provenance` disclosure exposes:

- exact source refs;
- commit/blob references;
- scene IDs;
- processing versions;
- dataset artifact paths;
- limitations.

No provenance information is deleted; it is re-layered for readability.

## 13. README and documentation

README must gain:

- `How to read the score`;
- explanation that score means partitura;
- public live demo;
- V0.2 track overview;
- satellite source/processing boundary;
- explicit experiment-vs-evidence distinction;
- non-goals and integrity rules.

A public reader should understand the product without opening implementation source files.

## 14. Error handling and fail-closed behavior

V0.2 must preserve the existing strict runtime boundary:

```text
untrusted/static artifact
      -> strict validation
      -> typed domain object
      -> core/UI
```

Required behavior:

- missing required satellite artifact -> dataset load failure;
- malformed satellite artifact -> load failure;
- unknown fields -> validation failure;
- invalid timestamps -> validation failure;
- invalid/non-finite indices -> validation failure or explicit missing record, according to the schema contract;
- missing preview for an otherwise valid observation -> no preview affordance, not a broken image;
- unusable segment -> explicit `MISSING` with reason;
- no automatic fallback to live GeoPlatform/GEE runtime data.

## 15. Testing strategy

Implementation must follow TDD.

Minimum required test surfaces:

### Contracts

- valid satellite artifact parses;
- unknown fields reject;
- invalid timestamps reject;
- invalid classes reject;
- unusable/missing record invariants reject inconsistent payloads;
- required manifest satellite artifact validates;
- unsafe artifact paths still reject.

### Loader

- required satellite artifact loads;
- missing required satellite artifact fails closed;
- malformed satellite artifact throws;
- no runtime external fallback occurs.

### Core

- satellite context aligns by segment;
- missing satellite segment remains missing;
- satellite does not alter access/weather/mobility states;
- human-readable labels do not replace internal IDs in core identity.

### UI

- intro appears once per session and can be reopened;
- public location labels/units are shown;
- weather/mobility/access missing states have plain-language explanations;
- satellite card shows source/date/indices/class when usable;
- unusable satellite context shows missing reason;
- raw provenance is secondary/collapsible;
- ML experiment is separate from territorial matrix;
- no UI copy asserts road condition, safety, opening, closure, authorization, or defect.

### Regression/integrity

Explicit tests must protect:

```text
missing != zero
PENDING != open/safe/closed
satellite signal != road condition
snow-like != snow on road
snow-like != road closed
candidate != defect
simulation != operation
```

Existing deterministic mobility benchmark, rule artifact, ML artifact, evaluation, TypeScript build, and Python suite remain part of the release gate.

## 16. Acceptance criteria

V0.2 is accepted only when all of the following are true:

1. A first-time non-specialist can understand the application purpose before seeing the dashboard.
2. The five Agua Negra locations are shown with human labels, km, and units.
3. Missing weather/mobility/access states explain why information is absent or unverified.
4. Satellite context is a strict, frozen, versioned artifact with deterministic classification rules.
5. A frozen satellite preview is shown when available without introducing runtime GEE/GeoPlatform dependency.
6. Satellite context is a primary territorial row.
7. ML candidates are visually separated into an experiment section.
8. Technical provenance remains fully available but secondary to human-readable sources.
9. No safety/transitability/closure/defect inference is introduced.
10. Node tests, TypeScript build, artifact reproducibility checks, Python tests, mobility benchmark checks, and ML evaluation all pass on the release candidate.
11. Vercel preview/production deployment succeeds.
12. README explains how to read the system without prior repo knowledge.

## 17. Explicit non-goals for V0.2

Do not add:

- Random Forest or another satellite ML classifier;
- live GEE queries from Territorial Score browser runtime;
- live GeoPlatform runtime dependency;
- live weather or GPS telemetry;
- road-condition inference;
- route opening/closure inference;
- safety or risk score;
- autonomous decision-making;
- WHAT_IF simulation;
- optimization;
- reinforcement learning;
- Monte Carlo;
- write-back into GeoPlatform;
- synthetic ground truth rendered as territorial evidence.

## 18. Future path

A later version may compare deterministic satellite rules with a labelled ML classifier, but only after a defensible labelled dataset and evaluation protocol exist.

A later scenario engine may consume Territorial Score state as input, but WHAT_IF simulation belongs in the simulation layer rather than this V0.2 context release.
